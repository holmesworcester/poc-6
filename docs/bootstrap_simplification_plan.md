## Design Doc Analysis and Conclusions

### Issue 1: `user_id = invite_id` — DESIGN DOC ERROR

**What the doc says:**
- Line 29: `user_id = id(invite(mode=user))`
- Line 80, 96, 343: `users(user_id=invite_id, ...)`

**Analysis**: The doc is internally consistent — it repeatedly says `user_id = invite_id`. This implies:
- Each `invite(mode=user)` creates exactly ONE user (1:1 relationship)
- The user's identity IS the invite that created them

**Why this is wrong**: User clarified "an invite can have many users." This breaks the doc's 1:1 model. A reusable invite must allow multiple different users to accept it.

**CONCLUSION**: The design doc has an error. The correct model is:
- `user_id = id(user_event)` (content-addressed hash of user event body)
- 1 invite can create N users
- Each user event is unique (different user_pubkey, timestamp, etc.)

### Issue 2: `user_pubkey = invite_pubkey` — DESIGN DOC ERROR

**What the doc says:**
- Line 59: `invite_pubkey (projects to user_pubkey)`
- Line 75: `user_pubkey is derived from the invite during projection`
- Line 198, 343: `users(user_pubkey=inv_u.invite_pubkey, ...)`

**Analysis**: The doc is internally consistent — it explicitly says `user_pubkey` comes from `invite_pubkey`. The keypair would be:
- Generated when creating the `invite(mode=user)`
- `invite_pubkey` stored in invite event
- `invite_private_key` sent in invite link to joiner
- After projection, `invite_pubkey` becomes `user_pubkey`

**Why this is wrong**: User clarified "user privkey/pubkey are unique to user and not shared by invite." Sharing keys between invite and user would mean:
- Anyone with the invite link could impersonate the user (sign as `signed_by=user_id`)
- Multiple users from same invite would share the same key (collision)

**CONCLUSION**: The design doc has an error. The correct model is:
- User generates their OWN unique `user_private_key` / `user_pubkey` pair
- `invite_pubkey` is ONLY used to verify `signed_by=invite_id` on the user event
- `user_pubkey` is stored IN the user event body (not derived from invite)
- `user_pubkey` is what verifies `signed_by=user_id` on first peer invite

### Corrected Identity Model

| Entity | ID | Public Key | Private Key | Notes |
|--------|---|------------|-------------|-------|
| network | `id(network)` | `network_pubkey` | discarded after bootstrap | Root of trust |
| invite(user) | `id(invite)` | `invite_pubkey` | in invite link | For verifying `user` signature |
| user | `id(user_event)` | `user_pubkey` | discarded after first peer | **Unique to user**, stored in user event |
| invite(peer) | `id(invite)` | `invite_pubkey` | in invite link | For verifying `peer_shared` signature |
| peer_shared | `id(peer_shared)` | `peer_pubkey` | kept for ongoing ops | Long-lived device key |

### Signature Verification Chain (corrected)
1. `user` event: `signed_by=invite_id` → verify with `invite(user).invite_pubkey`
2. `invite(peer)` for first peer: `signed_by=user_id` → verify with `user.user_pubkey` (from user event, NOT invite)
3. `peer_shared`: `signed_by=invite_id` → verify with `invite(peer).invite_pubkey`
4. `invite(peer)` for later peers: `signed_by=peer_shared_id` → verify with `peer_shared.pubkey`

### Key Insight: Two Keypairs in User Creation Flow

When accepting a user invite:
1. **Invite keypair**: `invite_private_key` (from invite link) + `invite_pubkey` (from invite event)
   - Used to sign the `user` event (`signed_by=invite_id`)
   - Verifier loads `invite_pubkey` from invites_user table

2. **User keypair**: `user_private_key` + `user_pubkey` (both generated by joiner)
   - `user_pubkey` stored IN the user event body
   - `user_private_key` used to sign first `invite(mode=peer)` (`signed_by=user_id`)
   - Verifier loads `user_pubkey` from users table

This separation ensures:
- Invite key proves "I have the invite link"
- User key proves "I am this specific user"
- Multiple users can accept the same invite (each with unique user_pubkey)

## Target Design (from NETWORK_ROOT_LINKING_DESIGN.md, with corrections)

### Core Principles
1. **Uniform DAGs**: Same invite→proof flow for first user/peer as later users/peers
2. **signed_by polymorphism**: Events use `signed_by` field (network_id | user_id | peer_shared_id | invite_id)
3. **No separate invite_proof**: The proof IS the signature on `user` and `peer_shared` events (signed_by=invite_id)
4. **First-class admin events**: `admin` is its own event type (not a group), signed by network_id (bootstrap) or admin peer (ongoing)

### Key Insight: Uniform Peer Linking

**The first peer must be added the same way as all later peers.** This is a major change.

Current flow (special case for first peer):
```
network creation → user created directly → peer created directly → admin granted via group_member
```

New flow (uniform for ALL peers including first):
```
1. network [root, has network_pubkey]
2. invite(mode=user) [signed_by=network_id, has invite_pubkey]
3. user [signed_by=invite_id, has its own user_pubkey]  ← user_id = id(user_event)
4. admin [signed_by=network_id, grants admin to user_id]
5. invite(mode=peer) [signed_by=user_id, verified with user_pubkey]
6. peer_shared [signed_by=invite_id, verified with peer invite's invite_pubkey]
```

**Key clarification**:
- `user_id = id(user_event)` (content-addressed hash), NOT invite_id
- User has its own `user_pubkey` (unique per user, NOT shared with invite)
- `invite_pubkey` is what verifies `signed_by=invite_id` on the user event
- `user_pubkey` is what verifies `signed_by=user_id` on the first peer invite

**Why this matters:**
- First peer uses `invite(mode=peer)` signed by `user_id` (verified with user's unique `user_pubkey`)
- Later peers use `invite(mode=peer)` signed by `peer_shared_id` (verified with `peer_shared.pubkey`)
- `peer_shared` is ALWAYS signed by `invite_id` (verified with peer invite's `invite_pubkey`)
- This eliminates special-case code paths

### Event Flow Diagram
```
network [no signed_by, root of trust]
    │
    ├── invite(mode=user) [signed_by=network_id, depends_on=network]
    │       │
    │       └── user [signed_by=invite_id, depends_on=invite(user)]
    │               │
    │               ├── admin [signed_by=network_id, depends_on=network+user]
    │               │
    │               └── invite(mode=peer) [signed_by=user_id, depends_on=user]
    │                       │
    │                       └── peer_shared [signed_by=invite_id, depends_on=invite(peer)]
    │
    └── (network_private_key discarded after bootstrap)
```

CREATE TABLE IF NOT EXISTS admins (
    admin_id TEXT NOT NULL,
    network_id TEXT NOT NULL,

### Phase 6: Rewrite `new_network()` Flow

**File:** `events/identity/user.py`

```python
def new_network(name, t_ms, db):
    # 1. Create local peer (for recorded_by, never shared)
    peer_id, peer_private_key = peer.create(t_ms, db)

    # 2. Create network event (root of trust)
    network_id, network_private_key = network.create(peer_id, t_ms, db)

    # 3. Create groups (all_users for membership, admins group NOT needed - using admin events)
    all_users_group_id, all_users_key_id = group.create(...)

    # 4. Create channel
    channel_id = channel.create(...)

    # 5. Create invite(mode=user) signed by network_id
    user_invite_id, user_invite_private_key = invite.create(
        mode='user',
        network_id=network_id,
        signed_by=network_id,
        signer_private_key=network_private_key,
        ...
    )

    # 6. Create user event signed by invite_id
    #    - Generate NEW user_private_key/user_pubkey pair (NOT derived from invite)
    #    - user_pubkey is stored IN the user event body
    #    - Sign with invite_private_key (signed_by=invite_id)
    user_id, user_private_key = user.create(
        invite_id=user_invite_id,
        invite_private_key=user_invite_private_key,  # for signing
        name=name,
        ...
    )
    # user_private_key is NEWLY GENERATED, not derived from invite

    # 7. Create admin event signed by network_id (grants admin to user)
    admin_id = admin.create(
        user_id=user_id,
        network_id=network_id,
        signed_by=network_id,
        signer_private_key=network_private_key,
        ...
    )

    # 8. Create invite(mode=peer) signed by user_id (FIRST PEER - same flow as later peers!)
    peer_invite_id, peer_invite_private_key = invite.create(
        mode='peer',
        user_id=user_id,
        signed_by=user_id,
        signer_private_key=user_private_key,  # derived from user invite
        ...
    )

    # 9. Create peer_shared signed by peer_invite_id (UNIFORM with all peer linking)
    peer_shared_id = peer_shared.create(
        invite_id=peer_invite_id,
        invite_private_key=peer_invite_private_key,
        peer_pubkey=peer_public_key,  # from step 1
        ...
    )

    # 10. Discard network_private_key and user_private_key (hygiene)

    return {...}
```

## Review Notes — Issues to Address

### Major Correctness Issues

#### 1. User ID Identity Model (CRITICAL - RESOLVED)

**Issue**: The original spec said `user_id = invite_id`. Our corrected plan says `user_id = id(user_event)`.

**Analysis**:
- The spec's `user_id = invite_id` model assumes 1:1 invite→user (deterministic, invite-derived)
- Our correction `user_id = id(user_event)` is required because **a single invite can create many users**
- Using hash(user_event) is correct because each user has unique `user_pubkey` and timestamp

**Resolution**: Keep `user_id = id(user_event)`. This is the correct model. The spec was wrong.
- `user_pubkey` must be stored IN the user event body (joiner generates fresh keypair)
- `invite_pubkey` is ONLY for verifying `signed_by=invite_id` on the user event
- Projections store `users(user_id=id(user_event), user_pubkey=event.user_pubkey)`

**Weight**: CRITICAL - foundational identity model, already resolved correctly in this plan.

#### 2. Admin Checks Use `recorded_by` Incorrectly

**Issue**: `is_admin()` may compare `recorded_by` to `peer_shared_id`. But `recorded_by` is the LOCAL peer ID, not the shared peer identity.

**Analysis**:
- `recorded_by` = local-only peer ID (never shared, used for partitioning)
- `peer_shared_id` = shared peer identity (content-addressed, DAG visible)
- These are DIFFERENT and should never be compared directly

**Resolution**:
- Admin state should be scoped by `recorded_by` for local view consistency
- Signer/subject resolution goes through DAG (lookup `peer_shared` → `linked_peers` → `user_id` → `admins`)
- Never compare `recorded_by` to `peer_shared_id`

**Weight**: HIGH - will cause subtle bugs if not fixed.

#### 3. Signer Resolution Ambiguity (`signed_by` Polymorphism)

**Issue**: Plan lacks deterministic resolution of signer type (network_id | user_id | peer_shared_id | invite_id). Inferring from context is fragile.

**Analysis**:
- All four ID types are content-addressed hashes (same format)
- Without explicit type info, we must probe multiple tables to find which one it is
- This is error-prone and inefficient

**Resolution Options**:
- (A) Add `signer_kind` field to events: `signer_kind ∈ {network, user, peer_shared, invite}`
- (B) Table-driven resolution: try tables in order until found
- (C) Use ID namespace prefixes (e.g., different hash lengths or prefix bytes)

**Recommendation**: Option (B) is simplest for now - document the resolution order and implement a shared `resolve_signer(signed_by, recorded_by, db)` function that returns `(signer_kind, pubkey)`.

**Weight**: MEDIUM - affects verification correctness, but manageable with careful implementation.

#### 4. Admin Signature Verification Source

**Issue**: Text says "verify with peer.pubkey" for ongoing admin. Must be `peer_shared.pubkey` (shared), not local-only `peer`.

**Resolution**: Already correct in our plan and design docs - use `peer_shared.pubkey` from `peers_shared` table, not local `peer`.

**Weight**: LOW - documentation clarity issue, implementation is correct.

#### 5. First Peer Flow Requires User Key Details (RESOLVED)

**Issue**: Plan says "user generates own keypair" but derivation/lifecycle is underspecified.

**Resolution**: Now documented in `ideal_protocol_design.md` under "Key Lifecycle (User Creation)":

1. **Invite keypair** (from invite link):
   - `invite_private_key`: received in invite link
   - `invite_pubkey`: stored in `invite(mode=user)` event
   - Used to sign the `user` event (`signed_by=invite_id`)
   - Discard immediately after creating `user` event

2. **User keypair** (freshly generated):
   - `user_private_key, user_pubkey = generate_keypair()` — fresh, NOT derived from invite
   - `user_pubkey` stored IN the `user` event body
   - `user_private_key` used to sign first `invite(mode=peer)` (`signed_by=user_id`)
   - Discard after first `peer_shared` is created

**Weight**: HIGH - security-critical key lifecycle. RESOLVED in design docs.

### Practical Implementation Risks

#### 17. Ambiguous `signed_by` in Storage

**Issue**: Without typed signer info, cross-table ID collisions could occur.

**Analysis**: Content-addressed IDs are collision-resistant (BLAKE2b-128 = 2^64 collision resistance). Risk is negligible for reasonable dataset sizes.

**Resolution**: Accept collision risk for POC. Production could add `signer_kind` if needed.

**Weight**: LOW - theoretical risk, negligible in practice.

#### 18. `is_admin()` Trust Boundary

**Issue**: Admin state must reflect DAG-valid rows only.

**Resolution**: Only query `admins` table, which is only populated by successful `admin.project()` calls. Blocked/invalid admin events are never inserted.

**Weight**: MEDIUM - ensure projection guards this.

#### 19. Event ID vs Identity ID

**Issue**: Keep event IDs (content-addressed) distinct from identity IDs.

**Analysis**: Our corrected model:
- `event_id` = hash of event blob (for content addressing in store)
- `user_id` = hash of user event (IS the event_id of the user event)
- `invite_id` = hash of invite event (IS the event_id)
- These are the SAME - identity IS the content-addressed event

**Resolution**: No distinction needed. `user_id = id(user_event)` is correct.

**Weight**: LOW - already resolved.

#### 20. Invite Signer Validation for First Peer

**Issue**: For `invite(mode=peer)` with `signed_by=user_id`, verification must use `users.user_pubkey` and block if missing.

**Resolution**: Phase 3 specifies this. Projection logic:
1. If `signed_by` is found in `users` table → it's a `user_id`, verify with `user_pubkey`
2. If `signed_by` is found in `peers_shared` table → it's a `peer_shared_id`, verify with `pubkey`
3. If neither found → block on missing dependency

**Weight**: HIGH - first peer linking correctness.
